# Independent review of the migration plan

Review date: 25 July 2026

Artifact reviewed: migration plan v1 (`PLAN.md`, 571 lines, 25 July 2026).
Corrected plan produced as a result: [PLAN-v2.md](PLAN-v2.md).

Mode: document audit only. No system was logged into, no DNS changed, no
application route called, no email sent, no backup restored and no migration
command executed. The only commands run were local `git` / `ls` / `cat` in this
repository, plus public documentation lookups.

Reviewer perspective: principal Drupal architect, Linux/Docker platform
engineer, security engineer, database and recovery specialist, migration
incident commander.

---

## 1. Executive verdict

### `APPROVE WITH BLOCKING CONDITIONS`

The plan's architecture is sound and the VPS-with-bounded-Compose choice is the
right one — no evidence was found that it cannot meet the stated safety
invariants, and a different server is not recommended. The phase order,
parity-first discipline, two-rehearsal requirement, GHCR-not-on-host build rule,
and the refusal to fold in a redesign are all correct instincts that most
migration plans get wrong.

However, the plan is not yet executable without operator improvisation on
exactly the steps where improvisation is fatal. Three defects are structural:
the DNS flip is scheduled *before* TLS issuance is proven, which puts the
least-reversible action ahead of the riskiest one; Drupal maintenance mode is
treated as a write barrier when it does not block privileged users, leaving a
real split-brain hole on o2switch; and rollback-after-writes is specified as a
"delta restore", which is not a defined operation for a Drupal database and is
never rehearsed in the backward direction.

Two more are gating rather than technical: OVH DNS write access — required for
both cutover *and* rollback — is recorded as **unavailable and blocking** in the
23 July ownership audit, and continuity of o2switch technical access through the
14-day rollback window is assumed rather than secured.

Resource containment is well-intentioned but not yet a guarantee: the ceilings
are per-container with no project-wide cap, so production + staging + the
restore-test project can request 106% of host CPU, and the plan's own 8 GiB stop
condition would fire during its own backup rehearsal.

Finally, the ownership audit records **two** intentionally public custom routes;
the plan addresses only one. None of this requires redesign — all of it is
correctable inside the existing architecture, and section 8 gives the ordered
patch list.

## 4. Architecture and isolation review

The shape is right. A separate Compose project, no Docker socket, no privileged
containers, `no-new-privileges`, dropped capabilities, an `internal: true`
backend network, no published database port, pinned digests, and no on-host
builds — this is a correct containment posture and materially better than most
Drupal deployments. `memswap_limit == mem_limit` is the correct expression of
"no swap" (`memswap_limit` is the *combined* memory+swap ceiling), and the plan
gets that semantic right where most get it wrong. Keep all of it.

What it does not yet do is make the containment *project-wide* or *enforced*.

### Recalculated Passerelle resource envelope

| Scenario | CPU quota | RAM ceiling | Swap | PIDs | Host headroom |
|---|---:|---:|---:|---:|---|
| Production only (4 containers) | **3.00 vCPU** (37.5% of 8) | **3,968 MiB ≈ 3.88 GiB** (12.5% of 31) | 0 | 704 | comfortable |
| Production + staging (staging unlimited in plan; assumed mirrored) | **6.00 vCPU** (75%) | ≈ **7.75 GiB** | 0 | 1,408 | tight on CPU |
| Production + staging + restore-test project | **8.50 vCPU — 106% of host** | ≈ **11.6 GiB** | 0 | 2,112 | **oversubscribed** |

Two consequences the plan does not draw. First, the three-project case requests
more CPU than the host physically has, and it occurs during the backup rehearsal
— a planned, scheduled activity, not an edge case. Second, at 20 GiB available,
that case leaves ~8.4 GiB free, which grazes the plan's own "confirmer au moins
8 GiB de RAM disponible" abort threshold: **the plan's rehearsal would trip the
plan's stop condition.**

The fix is P0-5's `passerelle.slice` — a parent cgroup makes the ceiling hold no
matter how many Compose projects the operator starts, which is exactly the
property a per-container limit cannot provide.

### What is a genuine guarantee

- **Memory.** `memory.max` on the cgroup is kernel-enforced. Under pressure the
  *cgroup* OOM killer fires inside Passerelle; neighbours are untouched. Drupal
  dies first — that is the correct trade and should be written down as deliberate.
- **CPU.** `cpu.max` is a hard quota, not a share.
- **PIDs.** `pids.max` is a hard cap; fork bombs stay contained.
- **Swap.** `memswap_limit == mem_limit` genuinely prevents Passerelle from
  adding to the existing 2.1 GiB of pressure. This directly addresses the
  host's existing memory-pressure history.
- **Port exposure.** No published DB port; loopback-only staging avoids the
  Docker-bypasses-UFW problem, because a `127.0.0.1`-bound publish creates no
  externally reachable DNAT rule.

### What remains monitoring-based, not guaranteed

- **Disk.** No quota on shared ext4. Alerting is detection, not prevention — and
  the alerting system itself is undefined (P1-13). P1-7's loopback image converts
  this into a real cap.
- **I/O.** `blkio` weights are proportional and probably inert under the host's
  likely scheduler. Until `io.max` values are read back from the cgroup, treat
  I/O containment as unproven.
- **Kernel.** Shared. AppArmor + seccomp + dropped caps + no-new-privileges
  reduce but do not eliminate this.
- **Docker daemon.** Shared, with `live_restore=false`. A daemon restart stops
  all 23 containers. Passerelle must never trigger one — no daemon config
  changes, no `docker system prune`, no global operations.
- **Ingress.** Shared Traefik. The P0-2 certResolver change requires a Traefik
  restart — a few seconds of 502s across all applications. Schedule it at T-7d,
  announced; never inside the window.
- **Network.** Today's `proxy` design is the weakest link (P0-6). A dedicated
  `passerelle-edge` network with Traefik attached live reduces Drupal's blast
  radius from "every application on the bus" to "Traefik only" — and
  `docker network connect` needs no restart, so it costs nothing operationally.

### Reverse proxy correctness

Not addressed in the plan and it will bite. Drupal needs
`$settings['reverse_proxy'] = TRUE` and `$settings['reverse_proxy_addresses']`
containing Traefik's address. Container IPs are dynamic, so set the **network
CIDR** (Symfony's trusted-proxy handling accepts CIDR notation) rather than a
literal IP that will change on the next recreate. Set `trusted_host_patterns`
for the production hostname, and separately for the `*.ts.net` name on staging.
Without this, client IPs are wrong in `watchdog`, flood control blocks the proxy
rather than the attacker, and any IP-based rule in the custom access modules
misbehaves.

### Secrets

`/etc/passerelle-intranet/secrets` at root-owned `0700` is right. Add: how the
containers read them (file mounts, not environment variables, so values do not
surface in `docker inspect` or logs), and confirm the GHCR pull token is scoped
`read:packages` only.

## 5. Data, configuration and integration review

**Source capture.** Strong overall — `composer.json`/`.lock`, patches, custom
modules and theme, PHP extension list, symlinks, permissions, checksums,
`composer validate`/`audit`. Three gaps:

1. **Parent-directory `.htaccess`.** The docroot is `…/intranet/www/web`. The
   plan collects `.htaccess` inside `web/`, but the nested `www/` wrapper (and
   the account root) very likely carry their own rewrites, redirects or access
   rules that are part of the live behaviour.
2. **cPanel-level PHP overrides.** MultiPHP INI Editor settings and any
   `.user.ini` change effective runtime configuration and are invisible in the
   Composer project.
3. **Encryption key material** (P1-17) — absent from the inventory entirely.

**Database migration.** The plan correctly identifies that active configuration
lives in the database and that a code-only export cannot rebuild the
application. That is the single most important insight in the document and it is
right. The weaknesses are the engine-selection rule (P1-2), the under-specified
dump command (P1-9), and the absence of post-restore hygiene. Add explicitly:
`lower_case_table_names` must match between source and target — it **cannot be
changed after MySQL 8 initialization**, and a mismatch breaks table resolution
at runtime.

**Public and private files.** Well covered — separate treatment, manifests,
orphan/missing detection, accent and special-character handling, upload limits.
Add: after restore, fetch a private-file URL **while logged out** and assert 403,
and assert that the private directory is not reachable through any public path.
Confirm Drupal's deny-all `.htaccess` in the files directories survives and that
the container's `AllowOverride` permits it (or that the private path sits
entirely outside `DocumentRoot`, which it should).

**Configuration.** Exporting from a clone is safe and correctly specified —
`config:export` writes YAML and does not mutate the database, so there is no risk
to authoritative production state. The residual risks are scrubbing and
placement (P1-11).

**Mail.** The transition logic is right — add Brevo DKIM, extend SPF, keep
Mailjet until the sender inventory proves nothing else uses it. Three additions:
the 300/day volume gate before committing to Brevo Free; a `p=none` DMARC record
published *before* the switch so the transition is observable; and confirmation
that bounces to the `@passerelle-trotteurs.fr` return path land in an OVH mailbox
someone actually reads. Note the Mailjet account itself is recorded as
inaccessible in the audit — so retrieving suppression lists may be impossible and
should not be a gate.

**DNS.** TTL handling is correct: lowering to 300 s at T-48h comfortably exceeds
the current ~3454 s TTL, so caches will have converged. Changing only the
`intranet` A record is right. Missing: CAA verification (P1-5), the zone-change
freeze covering the concurrent public-site migration (P1-15), and a full zone
export **verified restorable**, not merely taken.

**Cron.** The weakest area (P0-9). The plan controls one known job and assumes
that is the whole surface. It is not: other cPanel entries, `automated_cron`,
`drush cron`, and possibly `hook_cron` are all trigger paths, and core cron
itself may need to be newly scheduled if o2switch never had a separate entry.

**External services.** Geocoding, mapping, HelloAsso/Blagapro/Yapla redirects and
webhooks are all listed. Add a positive assertion per integration: for each one,
staging must be proven to hit a sink, a test key, or nothing at all — the current
"comportement de chaque intégration en staging" is a placeholder, not a control.
Outbound webhooks in particular can have real side effects with no email trace.

## 6. Rehearsal, cutover and rollback review

Reading the T-0 sequence as an incident commander:

**Ordering defect (P0-2).** Step 12 changes DNS; step 13 waits for the
certificate. The least-reversible action is placed before the most failure-prone
one, and step 13's wait is unbounded. If ACME fails, you are in a live outage
with DNS already moved and no timebox telling you when to abort. Pre-issuing the
certificate at T-7d collapses step 13 into a confirmation and removes the only
genuinely unbounded step from the window.

**Split-brain window (P0-3).** Between step 12 and full convergence, both hosts
are reachable. The old host is in Drupal maintenance mode, which stops anonymous
users but **not** privileged ones — precisely the people most likely to be
working during a migration. A `.htaccess` 503 lock closes this. It also gives you
the stop condition the plan lacks: propagation is complete when the o2switch
access log shows no further non-503 traffic, which is an observable fact rather
than a guess about resolver behaviour.

**Ambiguous commands.** Step 2 ("verify no user modification is still in
progress") and Étape 5's "vérifier les mises à jour de base sans les appliquer si
elles ne sont pas nécessaires" both require the operator to invent a procedure
under time pressure. Both are replaced with concrete checks in P1-16 and P1-10.

**Missing timebox.** Steps 13 and 14 have no clock. Add a decision clock to the
runbook: T+45 min — if the new site is not fully verified, abort and revert.
Without a pre-agreed number, the abort decision gets made emotionally at T+90.

**Rollback before opening.** Sound. DNS revert, stop `passerelle-prod`, re-enable
the old cron, lift maintenance. Add: the P0-3 unlock as step 0, and confirm that
no writes reached the new site (which is guaranteed if step 18 has not run).

**Rollback after opening.** As written, not achievable (P0-4). It requires three
things the plan does not provide: a defined restore operation (full, not delta),
a guarantee that o2switch received zero writes in the interim (P0-3), and proof
that a dump from the target engine version imports into the source engine
version. That third item is the one most likely to fail silently and is trivially
rehearsable — it belongs in rehearsal 2.

**Rollback latency.** Gated entirely by OVH DNS write access (P0-1). If only one
person holds it and they are unreachable, rollback time is unbounded regardless
of how good the technical procedure is. Both owners need independent, tested
access.

**Two-hour window — credible?** Yes, with the corrections. At ~291 MB the
mechanical work is roughly: final dump 1–2 min, transfer 2–5 min, restore
3–5 min, cache rebuild 1–2 min, counter/manifest comparison 10 min, DNS change
plus observation 10–15 min, functional smoke across roles 15–20 min, neighbour
verification 5 min. That is ~60–80 minutes with real slack. The window is
threatened by exactly three things, all now removed or bounded: unbounded
certificate wait (P0-2), unbounded propagation wait (replaced with a log-based
stop condition), and improvisation on ambiguous steps (P1-10, P1-16). The plan's
requirement that rehearsal 2 start from empty volumes, use only the runbook, be
executed or read by a second person, and be timed from zero is exactly right and
should not be relaxed.

**Rehearsal gap.** Two rehearsals are specified, both forward. Neither exercises
the backward restore into an o2switch-equivalent engine. Add it to rehearsal 2 —
it is the only proof that P0-4 is real.
